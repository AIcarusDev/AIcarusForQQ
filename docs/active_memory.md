# 主动记忆

主动记忆是一条独立的全局文本记忆路径。原有事件提取和故事线流程保持原有职责。
新路径没有会话分库、人物实体、消息引用、来源关系表、向量或图谱。
人物、背景、适用条件和主观判断均保留在自然语言正文中。

## 主模型工具

三个工具常驻 `memory_manage`（不可关闭），绑定项目 skill `memory-manage`，不依赖 Computer：

```javascript
await tools.memory_manage.memory_write({memories: ["第一条值得记住的内容", "第二条内容"]});
await tools.memory_manage.memory_search({query: "关键词"});
await tools.memory_manage.memory_read({id: "M000001", history: true});
await tools.memory_manage.memory_read({id: "B000001"});
```

`memory_write` 从执行器的本轮上下文取得 cognition（包括原生思考模式投影后的认知）。
主模型只填写记忆数组，无须再次填写认知。没有本轮认知时拒绝提交，防止悄悄保存空背景。
一次调用对应一个不可拆分批次，不截断或限额裁剪数组。
修正或撤回用自然语言提交，例如“撤回 M000001，这项判断已经不成立”。
引用的是系统内部记忆 ID，不是外部世界引用。

工具返回 `saved=true`、`batch_id`、`status=pending`，表示事务已经提交，尚未完成整理。
`processor_ready=false` 表示记忆处理模型尚未就绪；不应重复提交。
`memory_read(B...)` 可查看原文、认知、状态、重试次数和最后错误类型，以及整理后的记忆 ID。
`memory_search` 独立搜索全部长期记忆：正式活跃记忆、未删除事件、ready 故事线摘要。
各来源使用同一文字匹配与分页规则，不调用综合召回，也不采用实体、向量、图扩展或近期兜底。
结果 ID 分别为 M 开头、E 开头和 summary: 开头，均可通过 `memory_read` 读取。
主动记忆支持修订历史，批次 B ID 用于读取待整理材料。
`literal=true` 按完整文字匹配；默认中文分词，支持分页。没有命中就返回空，不使用近期兜底。

## 数据位置

权威存储为 `data/AICQ.db`，初始化仅新增三张表：

| 表 | 内容 |
| --- | --- |
| ActiveMemoryBatches | 认知原文、记忆数组、FIFO 状态、重试时间、处理结果；同时充当持久队列 |
| ActiveMemoryEntries | 当前正式记忆正文、版本、活跃/撤回状态和时间 |
| ActiveMemoryRevisions | 各版本正文及所属内部批次，用于修订回看 |

原始提交、当前记忆、历史版本都保存在数据库。批次和记忆 ID 只在该内部领域使用，
不保存 sender、session、message、source_ref 等外部锚点，不引入实体分类。

生成文件位于数据库旁的目录：

```text
data/memory/published/
  index.md
  entries/M000001.md
```

文件是当前活跃记忆的可重建镜像，不是第二个写入入口。主模型的搜索与读取直接查询数据库。
不会自动复制到 `/home/agent`，也不打开 Computer。文件通过临时写入加替换发布；撤回会移除镜像。
启动时重建视图；发布失败保留待发布状态并重试，不重新执行已完成的模型整理。

## 严格 FIFO 整理

单个 Core 进程只有一个 Worker，依序处理未完成批次：

1. 取最早批次，记录 `running` 和尝试次数。
2. 逐条检索本路径的正式记忆，总共选取最多 8 条相关记忆。
3. 一次调用记忆处理模型，输入完整 `cognition`、完整 `memories`、相关记忆正文及内部 ID。
4. 校验整个返回 JSON；只允许新增、更新、撤回或无变化。模型只能修改本次召回提供的 ID。
5. 在一个事务内写入本批全部修改、历史版本和完成状态。版本不符或任何修改无效，整批回滚。
6. 发布 Markdown，再继续下一批。

模型失败或返回不合法时，批次保留并以 5 秒起、最多 300 秒的退避重试。
**后续批次不能越过失败的队首**。用批次读取工具查看状态；修复模型配置或输出问题后继续。
空 changes 是合法的完成结果，必须附带说明。系统不把失败解释为空结果。

关机取消等待，不等待模型网络请求结束；模型线程仅返回文字，没有数据库写入权限。
未完成的 `running` 在下次启动恢复为 `pending`。完成状态与记忆同事务提交，因此崩溃不会造成半批写入，
也不会因重新消费一个已完成批次重复修改记忆。不同的工具调用仍视为不同批次。

此 Worker 面向项目已有的单 Core 进程部署；不支持多个 Core 进程共同消费同一数据库。

## 配置、召回和维护

`memory.active.enabled` 默认 true，控制新增提交、后台整理及自动召回；关闭后仍允许主动搜索/读取已有内容。
整理复用设置页面的 **记忆处理** 模型：需要启用 `memory.processing.enabled` 并配置 provider/model。
不用启用事件结构化或算法故事线。原有 `dry_run`、`solidify` 只属于事件/故事线维护，不控制主动提交。
模型未配置时批次仍保存，并在队首等待重试；修改配置生效后无需重新提交。

自动综合召回保持独立，在原有总数量预算内最多加入 3 条主动记忆；这不是主动搜索的限制。
组装请求时，仅从 memory 块移除可见工具历史中已有相同 ID 和正文的条目。
工具结果不被截断或改写；历史压缩移出后解除去重，新正文也不会被旧结果遮蔽。
这一路径只做现有分词与 SQL 文字匹配，没有新增向量服务；无结果时不填充不相关内容。
主动记忆在上下文中显示完整正文和内部 ID，条件和不确定性应保留在正文内。

“删除全部长期记忆”和“清空所有数据”会先停止 Worker，清理三张表并重建空文件视图，随后恢复 Worker。
已取消的旧模型调用不能将内容写回。正常开发验证使用临时数据库，不写真实认知、不发送 QQ 消息。

## 验证

`python -B -m pytest -q tests/test_active_memory.py`

覆盖批量及完整认知输入、FIFO/队首失败、整批回滚、旧版本拒绝、取消恢复、重复完成拒绝、
无变化处理、镜像失败恢复、撤回与修订、工具执行器认知传递及自动召回。
`tests/test_memory_manage.py` 覆盖常开工具与 skill 注入、全库搜索分页、按 ID 读取，以及可见历史去重与压缩后恢复。
这些是程序契约验证，不等同于真实整理模型的语义质量或实际 QQ 运行验收。
